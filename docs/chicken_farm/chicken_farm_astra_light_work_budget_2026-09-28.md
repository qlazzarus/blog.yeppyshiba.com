## 목표와 예산 요약

사용자 목표는 **ChatGPT Plus에서 Astra light로 5시간·주간 한도를 준수하면서 싱글플레이와 최소 serverless DB + WebRTC 멀티플레이를 완성**하는 것이다. 여기서 비용은 AI 개발 사용량과 그에 따른 구독 기간이다. Cloudflare 운영비는 이번 계산에 포함하지 않는다.

| 범위 | 잔여 소작업 추정 | 근거 수준 |
| --- | ---: | --- |
| 싱글플레이 완결 | 20~34개 | 아래 구현 경계와 완료 조건을 기준으로 한 초기 작업 분해 |
| 멀티플레이 추가 | 16~28개 | 2인 연결부터 8인 회귀까지 신규 구현 중심 |
| 합계 | 36~62개 | 이미 완료한 작업은 제외, 싱글·멀티 공통 기반은 중복 계산하지 않음 |
| 재작업 여유 25% 포함 | **45~78개** | 통합/환경/네트워크 문제에 대한 계획상 여유. 실측 신뢰구간이 아님 |

소작업은 하나의 확인 가능한 동작에 대한 코드 수정·관련 검증·인계의 묶음이다. 예: “미니맵 클릭으로 카메라를 이동하고 좌표 경계를 검증” 또는 “만료된 방 참가 요청을 거절하고 DB 정리를 검증”. 범위가 커지면 나눈다. **소작업 1개 = 메시지 1개 = 5시간 한도 1회가 아니다.** 이미 큰 UI 패킷 하나도 여러 소작업으로 나뉠 수 있다.

이 숫자는 구현 노력의 대략적 범위이며 모델의 고정 처리량을 뜻하지 않는다. 초기 3개 소작업 측정 뒤 작업 크기와 재작업률을 다시 산정한다. 현재 아트 생성 시간, 모든 원본 콘텐츠의 완전 이식, 자동 방장 이관, 경쟁전용 서버 판정, 음성/영상 채팅은 견적 밖이다. 최종 목표를 포기한다는 뜻이 아니라 해당 범위를 추가하면 별도 견적이 필요하다는 뜻이다.

## 현재 코드에서 확인한 경계

- `main.ts`의 `getSharedPlayerEconomy`, 건물 완료/제거 callback, `buildingEconomyAdapter.ts`가 존재한다. 공용 wallet 및 건설→경제 연결을 처음부터 만드는 견적으로 잡지 않는다. 실제 플레이 회귀와 잔여 불일치를 보완한다.
- 선택·명령 카드·건설·인벤토리·시장 판매·부화 경로가 있다. 경제와 전투가 합쳐진 한 판 전체의 통과 증거는 별개다.
- `config.ts`의 `combat`과 `combatSmoke`는 기본 off다. 실제 맵의 웨이브 통합과 게임 종료/재시작까지 검수해야 한다.
- `games/chicken-farm/src`에서 `RTCPeerConnection`, `RTCDataChannel`, `D1Database`, signaling 구현을 확인하지 못했다. 멀티는 연결·방·동기화·회귀를 신규 작업으로 잡는다.
- P0-1의 DBG/격자 기본 숨김 등은 반영됐지만 선택창 기술 문구 제거와 긴 텍스트 검수 등 원래 완료 조건 전체가 확인된 것은 아니다. 기존 “구현 완료” 표기를 모든 UI 완료로 확대 해석하지 않는다.
- 기존 7월 문서는 코드보다 오래됐다. 그 문서의 미구현 목록만으로 재구현 작업을 산정하지 않는다. 이번은 제한된 소스 대조이며 전체 기능 감사/플레이 테스트는 아니다.

DB 최소화는 개발 범위를 줄이는 데 도움이 되지만 동기화·복구 검증을 없애지는 않는다. 사용자의 “STUN 기록 등”은 **방/세션과 SDP·ICE 연결 정보의 임시 관리**로 구체화한다. STUN은 NAT 주소 발견 역할이고 DB의 방 기록과는 다르다. 영구 DB에 매 tick 상태를 쓰지 않으며 후보 정보는 교환 후 삭제/만료 처리한다. DB를 이용한 polling만으로 단순화하면 TTL·횟수 제한·재접속 중복 처리는 M2에서 검수한다. 장시간 시그널링 연결 또는 Durable Object를 선택한다면 그 변경도 M2 견적에 재반영한다.

## 실제 한도 측정

사용자 보고를 잔여율로 해석한 첫 기록이다. 정확한 관측 초 단위 시각은 없으므로 초기화 절대 시각을 만들어 쓰지 않는다.

| 기록 시각 | 모델 설정 | 5시간 잔여 / 초기화까지 | 주간 잔여 / 초기화까지 | 판정 |
| --- | --- | --- | --- | --- |
| 2026-09-28 16:10 KST 기록 | Astra light 목표; 앞선 작업은 여러 모델 혼재 | 61% / 3h 11m | 78% / 6d 17h | 기준 스냅샷 1건. Astra task당 소비 표본은 0건 |

현재 구간에서 39%p/22%p를 사용했다고 읽을 수 있지만, 이전 작업의 모델·시간·다른 프로젝트 소비가 섞여 있어 이를 닭농장 Astra light 비용으로 귀속하지 않는다. 앞으로는 다음 표를 채운다.

| Task / 시도 | 모델·추론·속도 | 시작/종료 KST | 5h 전→후 / 소비 %p | weekly 전→후 / 소비 %p | 검증 결과·완료 소작업 수 | 초기화·다른 작업 혼입 |
| --- | --- | --- | --- | --- | --- | --- |
| 측정 대기 | Astra / light(UI 표기 그대로 기록) / 확인 필요 | — | — | — | — | — |

- 같은 구간에서 `소비 %p = 시작 잔여율 - 종료 잔여율`. 사용률 표시인 UI라면 반대로 계산한다.
- 진행 중 초기화됐거나 다른 모델/프로젝트가 같은 한도를 썼으면 표본을 분리한다. 정수 반올림으로 0%p가 보여도 무료라고 판단하지 않는다.
- 파일 읽기·계획·리뷰·실패한 실행·재시도도 소모에 포함한다. 성공한 마지막 시도만 재서 비용을 낮춰 잡지 않는다.
- 먼저 SP-02 환경 확인, SP-05 건설 lifecycle, SP-06 경제 통합 검수 각 1개를 재고 임시 범위를 만든다. 이후 같은 종류 5개 이상을 모아 큰 쪽 소비량에 여유를 더해 예약한다. UI polish나 멀티 작업을 측정 때문에 선행하지 않는다.
- 5시간은 사용량 집계 구간이다. 모델이 5시간 일하거나 task 하나가 5시간 걸린다는 의미가 아니다. 주간 한도는 별도로 확인하며 `주간 예산 = 5시간 예산 × 구간 수`로 계산하지 않는다.

## 한도 준수와 완료 기간 계산

제안 운영 기준: 각 구간의 마지막 **20%를 여유분**으로 남긴다. 전체 주간 용량 중 닭농장 60%p, 다른 작업 20%p, 여유 20%p를 초기 배분안으로 둔다. 이는 서비스 규칙이 아니라 사용자가 조정할 개발 예산이다.

현재 스냅샷에서 20% 여유를 뺀 계획상 가용량은 5h 41%p / weekly 58%p다. 이미 사용한 22%p가 닭농장 예산인지 확인되지 않았으므로 남은 닭농장 전용 60%p를 확정할 수 없다. 이후 실제 다른 작업 예산도 차감한다.

```text
u5, uw = 다음 소작업 종류의 보수적 5h·weekly 예상 소비(%p)
R5, Rw = 최신 잔여율; O5, Ow = 남겨 둘 다른 작업 예산(%p)
지금 시작 가능한 동종 소작업 수
  = max(0, min(floor((R5 - 20 - O5) / u5),
               floor((Rw - 20 - Ow) / uw)))
```

실측 전에는 u5/uw가 없으므로 위 식으로 실행 개수를 확정하지 않는다. 가장 작은 검증 작업 1개부터 측정하고, 한도에 여유가 없으면 다음 작업을 시작하지 않는다. 한 번 시작한 turn의 소비 상한은 보장되지 않는다. 이 문서는 자동 중단 장치가 아니므로 매 작업 전후 사용량 화면 또는 CLI `/status` 확인이 필요하다.

아래는 **측정 전 민감도 예시이며 현재 속도 예측이 아니다.** 매주 닭농장에 60%p를 쓰고, 5시간 한도 및 사용자 작업 시간이 이를 허용한다고 가정한다.

| 완료 소작업당 실측 주간 소비가 다음과 같다면 | 주간 처리량 | 45~78개에 필요한 주간 예산 주기 |
| --- | ---: | ---: |
| 5%p | 12개 | 4~7회 |
| 10%p | 6개 | 8~13회 |
| 20%p | 3개 | 15~26회 |

실제 계산은 task 종류별 소비를 합쳐 `잔여 총 주간 소비 / 주간 닭농장 배정량`을 구한다. 현재 주기의 남은 예산과 초기화까지 남은 시간, 사용자가 작업하는 시간, 에셋 제공 일정도 반영해야 달력상 완료일을 말할 수 있다. 주간 한도가 충분해도 5시간 한도 때문에 실행이 밀리면 위 표보다 오래 걸린다.

추가 크레딧·API를 사용하지 않으면 초과금 목표는 $0이다. 개발에 필요한 기간이 길어지면 `실제로 추가되는 구독 갱신 횟수 × 계정의 월 결제액`이 개발 지속 비용이다. 이미 다른 용도로 Plus를 유지한다면 닭농장 때문에 늘어난 금액과 전체 구독액을 구분한다. 월 결제일·원화 실청구액·주간 소비 표본이 없으므로 현재 추가 금액을 확정하지 않는다.

## 모델 설정과 인계 규칙

- 앞으로의 예산 기준은 **Astra light**다. 과거 Terra medium 지시문은 검토 이력으로 보존하고 새 실행 지시문은 갱신한다. 여기서 `light`는 사용자 UI 명칭이며 CLI의 특정 enum으로 임의 치환하지 않는다. 문서 변경이 실행 중 모델을 전환하지는 않는다.
- 매번 Current Context, 해당 소작업 설명, 필요한 코드만 읽는다. 같은 문제의 수정·검증은 한 묶음으로 하고, 인계는 변경/검증/잔여/한도 네 항목으로 끝낸다.
- 환경 오류가 반복되면 동일 캡처 시도 반복 대신 S0의 원인 해결 소작업으로 관리한다. 서브에이전트·Fast 모드·API 전환을 한도 절약 수단으로 자동 실행하지 않는다.
- 다음 3개 측정 후 Current Context의 작업량·예상 주수·최신 한도 시각을 갱신한다. 데이터가 없으면 `미측정`으로 남기고 임의 %나 금액을 채우지 않는다.

공식 근거(2026-09-28 확인): [OpenAI 요금·사용 한도](https://learn.chatgpt.com/docs/pricing). Astra의 Plus 로컬 메시지 추정은 5시간당 5~45회이며 고정 한도가 아니다. 모델/문맥/추론/도구 사용에 따라 소비가 달라지고 주간 제한도 적용될 수 있다. 이 수치를 Astra light의 확정 처리량이나 소작업 수로 환산하지 않는다. 계정별 실제 잔여량과 초기화 시각이 우선이다.
